## Summary

Two slow-tier tests encode **contradictory** contracts about what the solver owes
a `time_limit`, and both currently fail. Neither can be repaired without deciding
the policy, so both ship as strict xfails in PR #1150 with nothing weakened.

## Side A — the deadline is overrun

`watercontamination0202`, measured at load 3.33 (§9 load gate):

| time_limit | wall | ratio |
|---|---|---|
| 30 s | 59.7 s | **2.0x** |
| 60 s | 89.4 s | **1.5x** |

#875 improved this class from 19.3x to 2.0x but did not close it: root setup is
still not fully inside the deadline. The test's threshold is 1.25x and is
**deliberately unchanged** — relaxing it would retire the contract rather than
meet it.

This is a class, not one instance:

| instance | overrun |
|---|---|
| casctanks | 2.7x |
| sonet23v4 | 2.32x |
| watercontamination0202 | 2.0x |
| nvs19 | 1.35x |

## Side B — honouring the deadline destroys the bound

`sonet23v4`'s dual bound comes from a single ~17 s uninterruptible operation. The
#654 deadline gating correctly declines to *start* it when the budget cannot
cover it, and the bound is then `None`:

| time_limit | bound |
|---|---|
| 2.0 s | **None** |
| 8.0 s | -473508.0000005656 |
| 30.0 s | -50587.97955518025 |

`test_issue654_deadline_root_setup.py::test_sonet23v4_bound_survives_the_deadline_gating`
asserts the bound survives; `test_875_root_setup_budget.py::test_watercontamination0202_honours_its_time_limit`
asserts the deadline is honoured. Satisfying either one as written breaks the
other, because the only way to stop overrunning is to decline long
bound-producing operations, which is precisely what loses the bound.

## What has to be decided

Which role-1 guarantee `time_limit` actually makes:

1. **Hard wall.** The solver returns by the deadline, and a truncated run may
   return `bound = None`. Side B's test is then wrong as written and must assert
   "bound is None **or** valid", never a bound.
2. **Soft target.** An uninterruptible bound-producing operation may overrun.
   Side A's 1.25x threshold is then wrong and needs a re-derived, documented
   bound on the overrun (not a nudge to whatever today's number is).
3. **Make the operation interruptible.** The only option that satisfies both
   tests as written, and the most work: the ~17 s root operation would need to
   yield a valid intermediate bound.

Option 3 is the honest fix. 1 and 2 both retire a contract someone is relying on,
so the choice is an owner decision, not a test edit.
