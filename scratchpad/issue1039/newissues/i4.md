## Summary

`_is_linear` in `python/discopt/_relax/gdp_reformulate.py` reports `False` for
`SumOverExpression` (the indexed summation `Σ[t0, t1, ...]`), even though such a
node **is** linear when every term is. The under-report is deliberate and is
documented in the code, but it is a capability gap worth closing properly.

## Why it is currently a deliberate False

PR #1150 tried admitting the node and it produced a **false optimality
certificate**. `_is_linear` is a shared gate with ~10 consumers, and several read
a `True` as "and I can therefore take this apart". These have no case for the
node:

| function | handles `SumOverExpression`? |
|---|---|
| `_hull_linear_substitute` | no — falls through to `_substitute_vars` |
| `_substitute_vars` | no — "Constant or unknown, pass through" |
| `_collect_variables` | no — returns `{}`, so vars are never disaggregated |
| `_body_at_zero` | no — raises (this is what refused loudly before) |
| `_bound_expression` | no — raises (big-M) |

With `_is_linear` widened, hull emitted

```
_hull_modes_d0_c0: Σ[3 terms] - (0 * y0) <= 0
```

— the disjunct body imposed **globally**, its selector coefficient collapsed to
zero and the disaggregated variables never created. On

```python
m.either_or([[dm.sum(x[i] - 1 for i in range(3)) <= 0.0], [x[0] >= 8.0]])
m.minimize(-(x[0] + x[1] + x[2]))     # xi in [0, 10], true optimum -30.0
```

both `auto` and `hull` returned `status=optimal, objective=-3.0, bound=-3.0`. A
dual bound of -3.0 is **above** the true minimum of -30.0, i.e. invalid. Three
loud refusals had become two silent wrong answers.

PR #1150 therefore reverted the widening. The `#1039` defect it was trying to fix
(the `exactly-one` row being dropped from the OA/LOA master) was fixed instead by
removing the redundant `_is_linear` pre-gate at those two call sites and relying
on `_extract_body_coeffs`, which answers with the row itself and so cannot
promise more capability than it delivers.

## What is left to do here

Teach the hull substitution family and the bounding path the node, then admit it
in `_is_linear`:

- `_collect_variables` — recurse into `.terms`
- `_substitute_vars` — rebuild the node with substituted terms
- `_hull_linear_substitute` — fold term by term, scaling constants by the selector
- `_body_at_zero` — sum the terms at zero
- `_bound_expression` — interval-sum the terms (closes the big-M route too)

With the first four applied on the #1150 branch, `auto` and `hull` both returned
**-30.0** on the repro above. That patch is verified but was **not** shipped in
#1150, because it is bound-changing.

## Why it needs its own PR and a panel

Admitting the node in `_is_linear` moves four other consumers:

- `solver.py:3068` — the structural linear-FBBT mask, whose docstring cites the
  #27a false-prune. Widening what FBBT treats as linear is bound-changing, and
  unsound if the linearity claim is ever wrong.
- `factorable_reform.py:684` — the aux-lift gate.
- `decomposition/benders/solver.py:114` — Benders route selection.
- `_relax/implied_integer.py:97` — reviewed as safe.

Under CLAUDE.md §5 this is the bound-changing regime: differential bound test,
feasible-point sampling, behind a flag, default-off until a corpus-wide
differential panel passes cert-clean **and** net-positive.

## Definition of done

1. The five functions above handle `SumOverExpression`.
2. `_is_linear` admits it.
3. `python/tests/test_1039_gdp_sumover_rows.py::test_sumover_disjunct_body_never_reports_an_invalid_bound`
   — already in the tree — **strengthens** rather than breaks: it currently
   accepts a loud refusal, and once the routes solve the model it asserts
   `-30.0`. It also already forbids any bound above the true optimum, so it
   catches a regression to the #1150 behaviour.
4. The §5 differential panel, cert-clean and net-positive.
